# Краткие заметки для соавтора

**Цель:** получить компактный и воспроизводимый пример сравнения вычислений одной модели на C# и TypeScript для статьи о переносе моделей.

## Что сделали и как

- Использовали AAPL, дневные свечи и период `[01.01.2022, 01.01.2024)`. Получилась 501 торговая дата: 03.01.2022–29.12.2023.
- Один раз загрузили историю Yahoo Finance, сохранили исходный ответ и общий файл OHLCV. Оба языка читают один и тот же локальный файл; повторный запуск не требует получения котировок или SQL Server.
- Подключили существующие сгенерированные модели Donchian из AspireTradingApp, сохранив их формулы. Настройки сделали одинаковыми: средние за 10 и 40 свечей, границы Donchian за 10 свечей. Прогрев выполняется внутри выбранного периода.
- Записали `Trading_CSharp.json` и `Trading_TypeScript.json`: реальные даты, позиция, события buy/sell, цены, индикаторы и исходный показатель `income`. Каждый файл занимает около 140 КБ вместо прежнего результата примерно на 56 МБ.
- Сохранили источник, контрольные суммы, настройки, версии окружения и commit. Скрипт `compare.mjs` сравнивает файлы и формирует `summary.json`; индикаторы дополнительно проверяются независимым расчётом по свечам.

**Результат:** все 501 записи совпали точно, максимальная численная разница — 0. В каждой реализации получено 231 событие buy и 231 sell; расширять период не пришлось. Два независимых повторных запуска дали побайтово одинаковые файлы для каждой реализации. Прошли 10 автоматических тестов и проверки итераторов на пустом наборе, одной свечe, нескольких свечах и повторном проходе.

## Какие проблемы обнаружили

- Исходные примеры использовали разные интервалы и параметры индикаторов. Для эксперимента выбрали соответствующую пару моделей и явно задали общие настройки.
- Оба итератора пропускали первую свечу. Исправили начало обхода и сброс итератора; теперь результат содержит все даты входного набора.
- Старый механизм пересчёта интервала в C# некорректно обрабатывал готовые дневные данные. Добавили явный режим чтения уже агрегированных свечей без этого пересчёта. Сам старый механизм полностью не перерабатывали.
- В прежнем большом результате поле `DateTime` содержало счётчик, а не календарную дату. В новых файлах дата берётся из самой свечи.
- Обнаружили особенности исходного учёта сделок: для short из `income` вычитается величина `entry − exit`, а состояние «открыто/закрыто» переключается при изменении типа позиции. Эту логику сохранили для сравнения реализаций. Значение `income` нельзя без отдельной проверки трактовать как финансовую прибыль.

## Что можно улучшить

1. Отдельно проверить и исправить учёт short/long, закрытия и развороты позиции; добавить независимый расчёт прибыли и тесты на заранее известных сделках.
2. Разобрать высокую частоту событий: после прогрева модель выдаёт событие на каждой из 462 свечей. Совпадение языков подтверждено, но корректность торговых правил требует самостоятельной проверки.
3. Для полноценного бэктеста определить момент сигнала и исполнения, исключить использование ещё недоступных данных, учесть комиссии, проскальзывание и открытую позицию в конце периода. Сейчас используется цена закрытия текущей свечи, комиссии и проскальзывание равны нулю.
4. Расширить проверку переноса на другие периоды, параметры и инструменты; добавить запуск в браузере и CI. Текущая проверка выполнена на Windows, TypeScript исполнялся в Node.js после сборки esbuild; полная проверка фронтенда через `tsc` не проводилась.

**Формулировка для статьи:** на зафиксированном наборе из 501 дневной свечи AAPL обе реализации модели дали одинаковые позиции, события и численные показатели. Этот эксперимент подтверждает эквивалентность вычислений в проверенном сценарии; прибыльность и финансовая корректность стратегии отдельно не доказаны.
